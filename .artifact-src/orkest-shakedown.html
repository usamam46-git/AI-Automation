00

Cold start

Five minutes. Get the stack honest before you build anything on top of it.

  1. Bring everything up and confirm all eight services.

    terminal
    cd infra && docker compose up -d
docker compose ps --format 'table {{.Name}}\t{{.Status}}'

    You want postgres, redis, minio, api, worker_workflow, worker_documents, worker_notifications, beat.

  2. Start the frontend — cd apps/web && npm run dev — and sign in at localhost:3000.

  3. Confirm your OpenAI key is stored for this org. Settings → OpenAI API key should show sk-••••94AA. Every agent call and every embedding in this run bills to it.

Worth knowing before you start

worker_documents and worker_workflow do not bind-mount src/ — only the api container does. If you change anything under src/workers/ today, those containers keep running the old code with no error anywhere. docker compose build worker_documents worker_workflow after any such edit.

Decide what to do with the seeded data

Your org currently holds the demo seed: two knowledge bases, three tools, three published workflows. You are about to build your own alongside it. Two clean options:

  • Leave it. Nothing you build will collide — names differ, and the guardrail tests below don't touch it. Recommended; it gives you a working reference if something you build misbehaves.
  • Start bare. Delete the three demo workflows, both KBs and the three tools through the UI. Order matters: a knowledge base 409s while a live tool still searches it, and a tool 409s while a published version still references it. So archive the workflows first, then delete the tools, then the KBs.
Why those 409s exist

Both are the same rule in two places: published means immutable, so anything a published version depends on cannot vanish underneath it. Drafts don't block — you're still editing those.

01

Your corpus

Put real documents in, watch them become vectors, then calibrate retrieval against them before a single workflow depends on it.

Choose your material

Pick one domain and three or four documents. The workflow later assumes a purchasing / spend-policy flavour, but anything with rules and thresholds works — an internal handbook, a supplier agreement, a travel policy, a security standard. What matters is that the documents contain specific, checkable statements: a spending limit, a required approval, a notice period. Marketing prose retrieves badly and gives you nothing to verify against.

AcceptedNotes
.pdfMust have a real text layer. A scanned page raises UnextractableDocumentError — there is no OCR, deliberately.
.docxParagraph text only.
.md / .txtSimplest to iterate on. Extension wins over the declared MIME type.

Hard ceiling: 20 MB per file.

  1. Create the knowledge base. Knowledge → New. Name it something you'll recognise in a tool dropdown later — Spend policy. Leave the embedding model on text-embedding-3-small.

    Why -small

    Both models are requested at 1536 dimensions, so they're interchangeable in the schema and the shared index — but -small is 6.5× cheaper, and you'll re-index while iterating. The choice is permanent in practice: embedding_model is deliberately absent from the update schema, because changing it invalidates every chunk already stored. Pick it once.

  2. Drop your files onto the dropzone. Each becomes a row that polls Queued → Processing → Indexed. Polling stops the moment nothing is in flight.

    Expect

    All documents reach Indexed within a few seconds each. A failure shows Failed with the actual reason on the row — that column exists precisely so a bad upload isn't a silent no-op.

  3. Drag the same file in again. It should report that it is already indexed and that nothing was charged.

    What you just proved

    Deduplication happens at upload, on a content hash of the bytes — not just on re-ingestion. That's the difference between a cost control and a retry guard, and it's what keeps an afternoon of iteration inside a few cents.

  4. Open the chunk inspector on your longest document. Read three or four chunks end to end.

    Chunking packs whole paragraphs rather than sliding a fixed token window, so a chunk should read as coherent prose. If your chunks cut mid-sentence, the source formatting is fighting the extractor — worth knowing now rather than after a bad answer.

Calibrate the score floor — do not skip this

The retrieval playground is the only place you can see what the cutoff would discard, because it searches with score_floor: 0 and draws the 0.3 default as a line instead of applying it.

  1. Ask a question your corpus definitely answers. Note the top score.
  2. Ask something completely unrelated — "what is the refund policy for parrots". Note that score too.
  3. Ask a near-miss: adjacent to your domain but genuinely not covered. This is the one that matters.
Expect

A good hit lands well above the line; the nonsense query lands far below it and is marked as discarded. If your near-miss sits above 0.3, your floor is too low for this corpus — remember the number, you'll set it on the tool in the next phase.

Trap

Cosine scores are only comparable within one corpus and one embedding model. A 0.42 here means nothing about a 0.42 in the demo KB. Calibrate per knowledge base, every time.

02

The registry

Three tools, one of each type — including a real external API on the public internet. Register them before you build the graph, so the builder can offer them.

How to read every config block in this document

The JSON blocks below and throughout phase 03 are the row as it is stored — not something you type. The tool dialog and the node inspector are ordinary forms: dropdowns, labelled inputs, a key/value editor for headers, a row-per-property builder for output schemas. There is no JSON textarea on the path you'll walk today, and nothing anywhere asks you to paste a UUID. The stored shapes are reproduced because a node override merges against them, and because these field names are what the error messages name when something is rejected.

Registry vs inline — the thing to understand first

A node can carry its tool config inline, or point at a registry row by tool_id. The merge is deliberately asymmetric: a node may override only body / body_fields / payload / payload_fields / query / query_fields — the per-usage wiring. The url, method, headers, action, knowledge_base_id and is_mutating stay registry-owned. Otherwise a node could re-point a reviewed endpoint while the publish gate went on reading is_mutating: false off a row that no longer describes it.

And inline always wins. If a node has both, tool_type beats tool_id. Use registry mode today — you want the audit rows it produces.

Tool 1 — retrieval over your corpus

Tools → New. Set Type to Knowledge search — the one field that is immutable after create, because changing it orphans the type-specific config. The rest of the dialog is four controls:

  • Search in — a dropdown listing this workspace's knowledge bases by name. Pick Spend policy. If the list is empty it tells you so rather than leaving you with a dead box.
  • Default question — spending approval threshold.
  • Passages to retrieve — 5.
  • Minimum score — whatever you calibrated in the last phase.

Which stores as:

name: policy_search · type: knowledge_search · mutating: no
{
  "tool_type": "knowledge_search",
  "knowledge_base_id": "<resolved from the dropdown>",
  "query": "spending approval threshold",
  "top_k": 5,
  "score_floor": 0.3
}

Default question is required even though every node will override it — a config with neither query nor query_fields is rejected outright, because a retrieval tool that cannot state its question is not executable.

Why a picker and not a field

The backend resolves the knowledge base against the organization_id taken from the run row, so a hand-typed id belonging to another tenant fails at execution with a config error rather than leaking anything. But failing at run time is a poor substitute for not offering the mistake — so the control only ever lists bases in your own workspace.

Trap — and note where it is enforced

A knowledge_search tool cannot be marked mutating; the API rejects is_mutating: true on one outright. In the dialog you won't find the switch at all — it is hidden rather than disabled, because there is no decision to present. Retrieval is read-only, and forcing an approval gate upstream of a pure read makes the gate routine, which is exactly what strips it of meaning.

Tool 2 — a real external API

This is the one that proves the platform reaches outside itself. Frankfurter is a live public FX rate service: no key, no signup, real data.

Type HTTP request, Method GET, the URL below, Timeout 15, and leave Headers empty — that control is a key/value editor with an Add header button, not a JSON field. Stored shape:

name: fx_lookup · type: http_request · mutating: no
{
  "tool_type": "http_request",
  "url": "https://api.frankfurter.app/latest?from=EUR&to=USD",
  "method": "GET",
  "headers": {},
  "timeout_seconds": 15
}
The URL is static — there is no interpolation

You cannot build /latest?from={{currency}}. State reaches a request through body_fields on a POST body, never through the URL. That's a real constraint on today's build; plan the graph around it rather than fighting it.

If Frankfurter is unreachable from your network, substitute https://postman-echo.com/get — you lose the meaningful data but keep the round trip.

Tool 3 — the mutating write

The only one flagged is_mutating. This is what arms the guardrail in phase 04.

Type ERP connector, then pick Action from a two-item dropdown and turn on Writes to an external system. There is no payload editor here by design — the dialog says so in as many words, because anything it collected would be replaced by the first node that wired a payload up. Stored shape:

name: erp_post_entry · type: erp_connector · MUTATING
{
  "tool_type": "erp_connector",
  "action": "create_journal_entry",
  "is_mutating": true,
  "payload": {}
}
Honest about what this is

erp_connector makes no network call. It returns MOCK-<uuid>. It exists so the mutating-action mechanism — the guardrail, the gate, the audit trail — can be proven end to end before a vendor adapter exists. Everything around it is real; only the far end is simulated.

03

The graph

Ten nodes. Two agents, all three tool types, a branch that rejoins, and a human gate in front of the only write. This is the most complex thing the engine can currently express.

  start_1
     │
  agent_1 ............... agent · reads the webhook payload
     │
  tool_1 ................ tool · knowledge_search → YOUR corpus
     │
  tool_2 ................ tool · http_request → api.frankfurter.app
     │
  agent_2 ............... agent · decides, cites, sets account_code
     │
  condition_1 ........... condition
     ├── requires_approval == true ──→ approval_1 ──┐
     │                                              │  human gate
     └── (else) ─────────────────────→ tool_3 ──────┤  http_request → echo
                                                    │
                                                tool_4 ... MUTATING
                                                    │
                                                 end_1

Create a workflow with trigger type webhook, open the builder, and drop the nodes.

You do not name the nodes — and the order you add them decides the names

Node keys are assigned by nextNodeKey() as <prefix>_<n> the moment a node lands on the canvas. Since 2026-08-20 the config panel's header is an editable key field, and renaming rewrites both ends of every touching edge and every node_outputs.<key> path that referenced it — but the graph below is written against the keys as assigned, so leave them alone today and the paths will match. The graph is keyed agent_1, tool_1, condition_1 … not extract, policy_lookup, route. Every dotted path below is written against the real keys.

Add the nodes in the order given here. The number is just a per-type counter, so adding the ERP tool before the retrieval tool makes it tool_1 and silently invalidates every path you copy from this page. Order: start, agent, tool (policy), tool (fx), agent, condition, approval, tool (echo), tool (ERP), end.

Two defaults that will catch you

Every Tool node opens on Inline config, not Registry tool — you must switch it on each of the four. And the inline panel states the real reason to prefer registry: “An inline tool leaves no row in the tool execution log — that trail needs a registry tool to point at.” That is a stronger argument than the override-merge asymmetry described above.

agent_1 agent · was “extract”

Turns the raw webhook body into structured fields. Note the anti-hallucination instruction — it matters more than it looks, because everything downstream cites these numbers.

node config
{
  "model": "gpt-4.1-mini",
  "temperature": 0,
  "input_fields": ["trigger_payload"],
  "system_prompt": "You read an incoming purchase request and restate it as structured data. Copy figures exactly as they appear. Never invent a value that is not present in the input.",
  "output_schema": {
    "type": "object",
    "properties": {
      "vendor":     { "type": "string" },
      "amount":     { "type": "number" },
      "currency":   { "type": "string" },
      "category":   { "type": "string" },
      "line_count": { "type": "integer" },
      "summary":    { "type": "string" }
    }

}
Every property is mandatory

The schema is normalised for OpenAI strict mode before it is sent: additionalProperties: false is forced, and required is filled with every declared property. There are no optional fields, and you do not control that array. If a value can legitimately be absent, tick Nullable on its row in the schema builder — that is what emits {"type": ["string", "null"]}. Omitting a property from required is not available to you and would not help if it were.

tool_1 tool · registry · was “policy_lookup”

Switch Source to Registry tool, then pick policy_search. The KB, top_k and score_floor render read-only — registry-owned. Override only the query:

node override
{
  "query_fields": { "query": "node_outputs.agent_1.summary" }
}

The agent's own summary becomes the retrieval query. That's the whole RAG hop.

tool_2 tool · registry · was “fx_rate”

Switch to Registry tool and pick fx_lookup. No override — the URL is static and it's a GET. This node exists to prove the platform makes a real outbound call and puts the response into graph state.

Expect in the run timeline

Output shaped { "status_code": 200, "body": { "amount": 1, "base": "EUR", "rates": { "USD": … } } }. Headers are never echoed — request headers routinely carry bearer tokens, and this output is rendered in the viewer.

This only works because of a fix on 2026-08-21

api.frankfurter.app now answers 301 at Cloudflare. httpx does not follow redirects by default, and a 3xx is below 500 and not retryable — so the node used to store { "status_code": 301, "body": "<html>…Moved Permanently…" } and the agent downstream reasoned over that HTML as though it were an FX rate, with nothing reporting a failure anywhere. get_http_client now follows redirects (max 5). Worth knowing because it is the exact shape of a silent tool failure: a successful-looking status and a body that means nothing.

Empty config — {}. A condition node carries nothing; the branching lives on its outgoing edges.

approval_1 human_approval

Empty config. There is no message field, and adding one is not the answer — the approval sentence the reviewer sees is derived from upstream node outputs at render time.

tool_4 tool · registry · MUTATING · was “post_to_erp”

Switch to Registry tool and pick erp_post_entry — the picker tags it with an amber writes marker. Override the payload wiring only:

node override
{
  "payload_fields": {
    "vendor":       "node_outputs.agent_1.vendor",
    "amount":       "node_outputs.agent_1.amount",
    "account_code": "node_outputs.agent_2.account_code"
  }

The mapping control is a two-column editor — destination key on the left, dotted state path on the right — with an Add mapping button. You are picking and typing paths, not authoring JSON.

What the editor catches, and the one thing it can't

create_journal_entry requires vendor, amount and account_code to be non-null. Two of the three ways to get this wrong are caught on the canvas: leave a required key out entirely and the field shows “Missing at run time: …”; mistype the root of a path and the editor warns that it is not a state root and will resolve to null.

What nothing catches is a typo further along a valid root. node_outputs.agent_1.vendr has a legitimate root, passes both checks, resolves to null, and fails the run mid-flight — after the approval was given. That is the one to proofread, and it is the only one.

The edges — and the one ordering rule

From → ToCondition
start_1 → agent_1—
agent_1 → tool_1—
tool_1 → tool_2—
tool_2 → agent_2—
agent_2 → condition_1—
1st condition_1 → approval_1node_outputs.agent_2.requires_approval eq true
2nd condition_1 → tool_3none — the fallback
approval_1 → tool_4—
tool_3 → tool_4—
tool_4 → end_1—
Create the conditional edge before the fallback

Outgoing edges are evaluated in order, first match wins, and an edge with no condition always matches. Draw the unconditional edge first and it swallows every request — the approval branch becomes unreachable and nothing warns you. If none match, the last edge is taken.

Available operators: eq neq gt gte lt lte in contains. There is no expression language and no eval — a structured field / operator / value triple is the whole DSL, on purpose.

The Value box parses what you type and reports what it decided: enter true and the hint under the field reads “Typed as a boolean”. Quote it to force a string — 0.8 is a number, "0.8" is text. Read that line rather than guessing.

Notice what this graph does to the guardrail

tool_4 is mutating, and the auto branch reaches it without passing an approval. Publishing still succeeds. That is ∃-semantics, and it is deliberate: a mutating node passes if any human approval exists among its ancestors, not if every path reaches one. Requiring every path would reject the reference workflows the platform was specified against. Know this before you rely on the gate as an absolute — it is a design-time prompt to think, not a runtime interlock on every branch.

04

Break it

Four deliberate failures. Do these before publishing for real — this is the part of the product worth demonstrating to anyone, and each takes under a minute.

All four ran on 2026-08-21 — and the canvas is faster than described below

Each test is written as “save, then try to publish”. In practice the canvas flags every one of them the moment you make the mistake, with the offending node outlined and the reason on hover — you never have to reach Publish to see it. Publish is still the authority and still returns a real HTTP 422; the toast just says “Publish rejected — see the highlighted nodes” and leaves the naming to the node itself. Do both halves: the inline flag is the daily experience, the 422 is the guarantee.

Test A — the mutating-action guardrail

  1. Delete approval_1 and reconnect route → post_to_erp directly.
  2. Save. It saves fine.
  3. Hit Publish.
Expect · HTTP 422

Rejected, naming post_to_erp specifically. Not a warning, not a toast you can dismiss — the version does not become publishable. Put the approval node back.

Why it saved but wouldn't publish

Draft and publish validate at different strictnesses, deliberately. The canvas autosaves after every node you drop, and every intermediate graph is broken by definition — so a draft only checks the two rules that would corrupt storage. Start/end presence, orphans, cycles and the approval walk are all publish-time.

Test B — a cycle

Drag an edge from assess back to extract. The canvas should flag it inline before you even try to publish. Loops are not supported; the compiler builds a DAG.

Test C — an orphan

Drop a bare agent node on the canvas and connect nothing. Save — fine. Publish — rejected. Delete it.

Test D — a tool that vanishes underneath a node

Which of the two outcomes you get depends on whether anything published still points at the tool, so run both halves.

  1. Published reference → 409. Tools → fx_lookup → Delete. It is refused: “Cannot delete tool because 1 node(s) in published workflow version(s) reference it.” Note that this is rendered in the dialog, not as a toast you might miss.
  2. Draft-only reference → 204, then unknown_tool. Register a throwaway HTTP tool, point tool_2 at it in the draft, then delete it. The delete succeeds — a draft is still being edited and does not block — and the node turns red on the canvas with “tool_2 points at a tool that is no longer in the registry.” Re-select fx_lookup.
Both deletes are SOFT

The row is flagged inactive, never removed: tool_executions.tool_id is NOT NULL with ON DELETE CASCADE, so a hard delete would erase the very audit trail the mutating-tool rule exists to create. The dialog says as much — “Existing runs and the tool's execution history are kept.”

Now fix everything and publish for real. Note the version number.

05

Sign & fire

Generate the signing secret, build a signed request by hand, and confirm that forged ones are indistinguishable from unknown ones.

  1. On the workflow detail page, open the Webhook secret card and generate one.

    Shown exactly once

    Copy it now. It is encrypted at rest, not hashed — HMAC verification needs the plaintext — and there is no code path that reads it back out. Lose it and your only option is rotation.

  2. Save this script and fill in the two constants at the top.

fire.py — the only thing you need to trigger a signed run
import hashlib, hmac, json, time, urllib.request

WORKFLOW_ID = "<workflow uuid from the URL>"
SECRET      = "<the secret you just copied>"
URL = f"http://localhost:8000/api/v1/triggers/workflows/{WORKFLOW_ID}"

payload = {
    "request_ref": "PR-4471",
    "requester":   {"name": "A. Novak", "department": "Sales"},
    "vendor":      {"name": "Acme Vendor LLC", "supplier_ref": "SUP-0442"},
    "currency":    "EUR",
    "lines": [
        {"description": "Component assembly AC-2291-B", "qty": 120,
         "unit_price": 35.0, "line_total": 4200.0}
    ],
    "total": 4200.0,
}

body      = json.dumps(payload).encode()          # sign the EXACT bytes you send
timestamp = int(time.time())
material  = f"{timestamp}.".encode() + body
signature = "sha256=" + hmac.new(SECRET.encode(), material, hashlib.sha256).hexdigest()

req = urllib.request.Request(URL, data=body, method="POST", headers={
    "Content-Type":    "application/json",
    "X-AAP-Timestamp": str(timestamp),
    "X-AAP-Signature": signature,
})
with urllib.request.urlopen(req) as r:
    print(r.status, r.read().decode())
Expect · HTTP 202

Accepted, with a run id. The run appears in Executions within a second or two.

Two details in that script that are the design

The timestamp is inside the signed material. That's what makes the five-minute freshness window enforceable — change the timestamp to dodge expiry and the signature no longer matches, so a captured request cannot be replayed forever.

The signature covers the exact bytes sent, never re-serialised JSON. Re-encoding payload separately for signing and sending is the classic way to produce a signature that doesn't match the body — key order and spacing both change the hash.

Now forge it

Run three variants and compare the responses byte for byte:

  • Replace the signature with "sha256=" + "0"*64.
  • Set timestamp = int(time.time()) - 4000 (outside the window).
  • Point WORKFLOW_ID at a random UUID that doesn't exist.
Expect · three identical 401s

Same status, same body, no hint about which failed. This is the only unauthenticated route in the product; a helpful error here would turn it into an oracle for enumerating workflow UUIDs across every tenant with no credentials. The missing-secret path even runs a dummy HMAC so the miss costs the same wall-clock time.

And check the quota wasn't touched

Forged requests must not consume run quota — otherwise anyone knowing a workflow UUID could exhaust a tenant's whole day. The claim happens after the signature verifies. Your Executions list should show only the one genuine run.

06

The gate

Watch a real run hold, read the forensics, then decide it. Both ways.

  1. Open the run from Executions. It polls every ~2.5s and stops on a terminal status.

  2. Walk the timeline node by node. This is the payoff for everything above:

    • extract — structured output, real prompt/completion token counts, real USD.
    • policy_lookup — hit_count and the actual chunk text with scores. Read the chunks. If they're irrelevant, your floor or your query mapping is wrong, and nothing downstream can recover from it.
    • fx_rate — a live rate from the public internet, sitting in your graph state.
    • assess — check policy_citation against what policy_lookup actually returned. This is the hallucination test. A citation that doesn't appear in the retrieved text means your prompt isn't holding.
    • post_to_erp — still pending. Nothing has been written.

  3. Read the approval prompt. It should name the vendor and the amount, derived from upstream outputs. If it falls back to a generic headline, that's the derivation deciding it couldn't read a figure honestly — by design it never invents one.

  4. Approve, with a comment. The second leg runs; post_to_erp returns MOCK-…; the run completes.

Check the duration

Total duration should include the time it sat waiting for you, not just the post-approval leg. A paused run costs nothing while it waits — the Celery task exits and the graph state lives in the checkpoint table, so a second task resumes it. That's why the timeline can span minutes with no worker held open.

  1. Fire it again and reject. Run status → rejected, and post_to_erp never executes.
  2. Fire a third time with a small amount (change total to 85.00) so assess sets requires_approval: false. It should take the auto_note branch, echo your mapped fields back, and complete without stopping.
What actually happened on 2026-08-21 — read this before demoing

The amounts behaved backwards, and the reason matters more than any other note on this page. The EUR 4,200 request did not hold: agent_2 set requires_approval: false and it was posted to the ledger with no human involved. The EUR 85 one did hold. The policy corpus is unambiguous that anything at or above EUR 1,000 needs approval, so this is not the corpus being wrong.

The cause is one mapping. tool_1 searches on node_outputs.agent_1.summary — a product description — so it retrieves the account coding guide and never the spend-authority threshold table. On the 4,200 run retrieval came back confident and on-topic (it found the coding guide's worked example for this exact part number), so the agent answered confidently and wrongly. On the 85 run retrieval was vague, so the agent escalated. The gate is firing on retrieval uncertainty, not on risk.

This is what ∃-semantics costs in practice: the auto branch reaches the mutating node with no gate, so the safety of the whole graph rests on one LLM boolean. Fixes worth considering — retrieve against the decision rather than the description, add a second retrieval for thresholds, or put a deterministic value condition upstream of the branch so money decides rather than prose.

Then look at the dashboard

Success rate should read 100% with a sample size of 2, not 67%. Rejected runs are excluded from the denominator on purpose: a rejection is the gate working, and counting it as failure would mean an organisation's score drops the more carefully it reviews.

07

Other triggers

Two more entry points, ten minutes.

Manual, with a payload

Workflows → row menu → Run now. Paste the same JSON body into the trigger-payload box. Identical execution, no signature. Blank input parses to {}, so one-click still works for graphs that don't read a payload.

Cron

Clone the workflow, set trigger type schedule, and give it a cron a couple of minutes out. Crons evaluate in the org's IANA timezone and convert to UTC — 0 9 * * 1-5 means 9am local.

Expect

beat ticks every 60s; the run appears on its own with actor_type: system in the audit log, and next_run_at re-arms to the next boundary.

Two things that will confuse you if you don't know them

Catch-up is suppressed. A workflow six hours overdue fires once and re-arms from now — it never replays the backlog. Deliberate: the alternative is an unattended spend spike.

A draft carrying a cron never fires. Only published workflows with a current version are picked up. Sub-minute crons are rejected outright.

Then turn it off

Archive the scheduled clone when you're done. An unattended cron pointed at a workflow you're still tuning is the one realistic way to burn an LLM budget overnight.

Roles and members

  1. Settings → Roles & permissions. Expand the matrix. Note that Viewer has no audit-trail tick despite holding a read-everything wildcard — those rows carry actor identity and client IPs, so three read permissions are deliberately exempted from the wildcard.
  2. Invite yourself at a second address as Viewer. Copy the link — no email is sent, and the link is unrecoverable once the dialog closes.
  3. Open the link in a private window. It should name the org and the role, and refuse to be accepted by any account other than the addressed one.
  4. Accept as the new user, switch org, and confirm the sidebar's Audit log renders a locked card rather than data.
  5. Back as Owner, use Change role… and read the gained/lost diff before applying it.
  6. Try to remove yourself. 409 — the last active Owner cannot be removed, because no endpoint could repair an org with nobody able to administer it.

The quota

Your dev cap is 50 runs/day, so you won't hit it by accident today. To see the 429, drop DAILY_RUN_QUOTA_PER_ORG to 2 in infra/.env, restart api, and fire three times: 202, 202, 429, the last carrying a Retry-After counted to the next 00:00 UTC. Put the value back.

No audit row on this path — corrected 2026-08-21

An earlier version of this page said a workflow.run.quota_exceeded row appears. It does not, on the HTTP paths. That action is written only by the schedule tick, which cannot raise an HTTP status and would otherwise skip a cron run silently. A tenant that exhausts its quota through the API or a webhook leaves no trace in the trail an admin would actually look at.

Ceilings

What will not work today, so you don't spend the morning discovering it. Every one of these is a decision with a reason, not an unfinished edge.

If you tryWhat happens, and why
A subgraph node It's in the palette and raises if invoked. Composition is not built.
An agent that calls tools itself Not supported. The OpenAI function-call array is built and tested; the loop isn't — because tool calls an agent emits have no node in the graph, so the publish-time guardrail structurally cannot see them. Shipping it without a runtime refusal would hollow out the product's main safety property.
python_function or mcp tools Rejected by name at create time, not stored as rows that explode later.
A loop / retry cycle Rejected at publish. The compiler builds a DAG.
Variables in a tool URL No interpolation. State reaches a request through body_fields only.
A scanned PDF Fails loudly. No OCR — a document that silently indexes to nothing is a KB that answers "I don't know" forever with nothing explaining why.
Keyword / hybrid search Dense vectors only. The full-text index exists and is unqueried — deliberately cut first.
Transferring ownership Owner isn't assignable in either direction. It has different consequences from a role change and deserves its own reviewed operation.
Live run updates Polling, not WebSockets. Every poll stops when nothing on screen can still move.
A real ERP write erp_connector is a mock returning MOCK-<uuid>. Everything around it is real.

Graph state — the dotted paths

PathWhat's there
trigger_payloadThe webhook body, or the Run-now box, verbatim.
node_outputs.<node_key>That node's output, keyed by its node key. An agent's parsed object sits here directly — node_outputs.agent_1.amount, not .output.amount. Keys are auto-assigned (agent_1, tool_1, …) and are renameable from the config panel header, which rewrites every dotted path that referenced the old key.
organization_idSeeded from the run row. Never from node config — that's what scopes retrieval.
run_idThis run.

A path that doesn't resolve returns null rather than raising. The mapping editor flags an unrecognised root before you leave the canvas, but everything after the first dot is unchecked — so proofread the tail of every path.
